## Fachliches Verfahren

**Zentrale Methode:** erst Code-/Consumer-Scope verstehen,
dann die **kleinste vollständige** Lösung suchen:
nicht bauen → vorhandenen Code wiederverwenden →
Standardbibliothek/Plattform → vorhandene Dependencies →
minimale eigene Änderung. Dabei Security, Validierung,
Accessibility, Datenverlustschutz und notwendige Tests
**nicht** wegoptimieren.

**`ponytail-review`** bewertet tatsächlichen Diff mit
Aufrufern, Security, erwarteter Last, fehlenden relevanten
Tests und Lean-/Reuse-Findings. Read-only.

**`ponytail-audit`** kartiert Entry Points und Datenflüsse,
priorisiert belegte Defekte/Regressionsrisiken sowie
unnötige Komplexität im gesamten Repo. Read-only.

**`ponytail-debt`** sammelt bewusst akzeptierte
`shortcut:`-Kommentare samt Grenzen/Upgrade-Trigger;
kein generischer TODO-Scraper.

`ponytail-gain` zeigt **historische Herstellerzahlen**,
ist kein projektspezifisches Erfolgsmesswerkzeug.
`ponytail-help` ist reine Bedienhilfe.

## Beobachteter Herstellerbenchmark (nicht unabhängig repliziert)

[Agentic-Benchmark](https://github.com/DietrichGebert/ponytail/blob/main/benchmarks/results/2026-10-07-agentic.md):
39 Aufgaben × 5 Durchläufe × 3 Vergleichsarme
= 585 Claude-Code-Sessions laut Bericht,
Opus 5.5, Default Effort, Headless, ohne Shell für die
Agenten. Verglichen wurden Bare Agent, früherer
Ponytail und Ponytail 5. **Relative Herstellerangaben
gegen ohne Skill:** `-53 % Codezeilen`,
`-45 % Output-Tokens`, `-41 % Zeit`,
`-26 % Kosten`. Nicht als Prognose für KI-Regeln
oder den aktuellen zusätzlichen Band-/Hook-Aufwand
von 5.3.2 behandeln.

Bei den **18 Fällen mit versteckten ausführbaren
Checks**: 87/90 (96,7 %) vs. 86/90 (95,6 %)
bestandene Runs; die Differenz ist gering.
Weitere 21 Aufgaben wurden anders beurteilt
(teilweise LLM-Judge und erfolgreiche Abgabe);
weniger LOC dort beweisen weder
Scopevollständigkeit noch Safety.
Der Herstellerbericht benennt selbst
ein problematisches Privacy-Szenario,
das alle Vergleichsarme nur in 2/5 Runs
bestanden. Es gibt veröffentlichte Tasks
und Reproduktionsanleitungen, aber hier
**keine** unabhängige Ausführung.

Nicht jede Reduktion heißt bessere Wartbarkeit
und nicht jeder Test prüft das entscheidende Verhalten.
Deshalb **Outcome vor Lines/Cost**.

## Risiken einer vollständigen Pluginaufnahme

| Oberfläche | Beobachtung | Entscheidung für PT-01 |
| --- | --- | --- |
| Globaler Always-on-Modus | `SessionStart`, `UserPromptSubmit`, `SubagentStart` injizieren Persona in Sitzung/Subagenten, Default `full` | **Nicht** in KI-Regeln global aktivieren; Bootstrap/Owner hätten Vorrang |
| Node-Hooks | können Konfigurations-/Flagdateien schreiben, Codebase-Map starten und Status-/Modus-Handling verändern | **Keine Hooks ausführen** ohne separaten Runtime-/Supply-Chain-Audit |
| Band/Board | speichert Nutzungs-/Sessionmetrik lokal; optionale Webhookkonfiguration kann Taskdaten/Metadaten senden | **Nicht aktivieren**, keine Sessions importieren, kein Webhook |
| Versionsdrift | Plugin 5.3.2; Benchmark „Ponytail 5“ vom 07.10. | Benchmark nicht ohne erneute Messung der heutigen Plugin-Konfiguration zurechnen |
| Dokumentation | `shortcut:`-Kommentare greifen in lokale Codekonventionen ein | Nur bei konkretem Nutzen und Projekt-Owner-Genehmigung |
| Scope/Abdeckung | 20 Hostadapter/Regelkopien; Skills und Hooks hostabhängig | Keine universelle Claude-/Codex-Parität aus README ableiten |
| Selbstinstruktion | Fremde `SKILL.md` und Hooks haben operative Verhaltensanweisungen | Bis zu `skill-security-review` untrusted Referenz; niemals über `AGENTS.md` stellen |

## Abgleich mit KI-Regeln-Ownern

| Ponytail-Teil | Bereits vorhanden | Offene Hypothese |
| --- | --- | --- |
| Core: minimales vollständiges Coding | `Workflows/Software-Feature.md`, `code-review`, `tdd`, `verification-loop` | Frühere, konkretere **Reuse-before-Write**-Entscheidung statt bloßem KISS-Review |
| `ponytail-review` | `Programmieren/Skills/code-review/SKILL.md` + `diagnose` | Mehr echte indirekte Consumer-Fehler, weniger Stil-/Overengineering-Scheinfunde |
| `ponytail-audit` | `code-review`, `architecture-review`, Fachreviews | Risk-first Entry-Point-Audit ohne Architektur-Overkill |
| `ponytail-debt` | `Workflows/Skill-Verbesserung-aus-Evals-und-Fehlern.md`, allgemeine Issues | Geringfügiges optionales Debt-Ledger mit **reellem Revisit-Trigger** |
| `ponytail-gain` / `help` | Evaluation / Dokumentation | Kein neuer Skill nötig |

**Wichtig:** „KISS“ steht bereits im bestehenden
`code-review`; PT-01 darf ihn nicht künstlich
verschlechtern. Ein zusätzlicher globaler
„Simplify“-Overlay wäre ohne positive Outcomes
unnötige Pflichtkontextlast.
